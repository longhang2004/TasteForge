# Surface purpose, targeted edits and annotated evidence

This source update applies three ideas studied in [Impeccable](https://github.com/pbakaus/impeccable) and its [Slop teaching page](https://impeccable.style/slop/), inspected 1 November 2026. It adds original TasteForge guidance and a gallery of this repository's own captures. The imported MIT reference dataset, CLI ranking and CLI command surface are unchanged.

## 1. State the visitor's purpose on each surface

[Surface purpose](../skills/tasteforge/references/surface-purpose.md) distinguishes deciding, working, reading and exploring as lightweight planning lenses. The same organisation's acquisition page, operational workspace, guide and project archive can have different priorities. A purchase page can combine a primary decision with artifact inspection; these are not rigid templates.

Record the target, actual visitor success, evidence/assumptions, fixed choices, information relationships and task check in the existing `UX_PLAN.md` or project guidance. Read existing briefs and design-system truth; do not create a mandatory new `PRODUCT.md`, overwrite an established system or add unsupported fields to the strict CLI brief/DNA schema.

The concept was informed by [Impeccable's skill modes](https://github.com/pbakaus/impeccable/blob/main/skill/SKILL.src.md). TasteForge's vocabulary and instructions are original adaptations; the upstream skill is not loaded as an instruction layer.

## 2. Refine a named target for a concrete outcome

[Targeted refinement](../skills/tasteforge/workflows/targeted-refinement.md) supports reducing clutter, clarifying meaning, adapting to context and adjusting emphasis. The current audit workflow routes to it. These are agent editing intentions, not additional CLI commands.

Each finding names state/width, evidence, consequence, edit and any intentional exception. A repeated quantity can support comparison and confirmation; a coloured failure rule can accompany explicit error text. Keep those relationships when removing actual redundancy. A small copy/focus fix should preserve layout and tokens, without forcing new prototypes or a replacement style.

For rendered critique, record the initial task/design observations before reading detector results where practical, then reconcile the evidence. Disclose the actual process if detector findings were already seen. This is informed by [Impeccable's critique separation](https://github.com/pbakaus/impeccable/blob/main/skill/reference/critique.md) and [distill's editing intent](https://github.com/pbakaus/impeccable/blob/main/skill/reference/distill.md). TasteForge does not adopt its mandatory delegation/approval procedure, numerical taste scoring or automatic context-engine setup.

## 3. Explain changes with real annotated captures

The [design gallery](../examples/design-gallery/README.md) uses eight unchanged captures from the inventory example: three actual repairs and one structural comparison. It labels full-page versus viewport framing, viewport dimensions, scroll position, authored notes and original evidence links. Image/trace hashes and region bounds are verified.

The gallery includes successful retained choices, not a collection of banned appearances. In particular, the table remains for comparison, explicit units remain, and failure retains its labelled coloured rule. The two mobile structures are labelled alternatives rather than being recast as a before/after success story.

This teaching approach was informed by [Impeccable's annotated examples](https://impeccable.style/slop/). Its pages describe deliberately exaggerated examples and distinguish source, browser and design-review evidence. The TasteForge gallery uses only this repository's actual artifacts and original explanations. Its overlays are authored, not output from a new browser detector. Neither source's illustrative gallery establishes representative-user outcomes.
