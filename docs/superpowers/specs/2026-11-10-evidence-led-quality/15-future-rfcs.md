## 1. Sequence and independent tracks

The first useful increment is small: source-linked cases and an on-demand copy/state reference, evaluated against existing material. A registry helper, new composition catalog, rendered audit and fresh human study are not prerequisites. Later tracks start only when they answer a specific product question or remove an observed maintenance burden.

## 2. WP-A/B: recommended next increment

Question: can TasteForge make copy information value and secondary-state continuity easier to inspect without making every task slower or aesthetically restrictive?

Inputs are the inspected sources in Spec 09, current conditional guidance, the seed distinctions in Spec 10 and selected existing artifacts. Deliver a small reviewed set with legitimate conventional examples, plus the short reference proposed by Spec 11. Keep the corpus and full research bundle outside the default skill reading path.

Use E0/E1 first. If an existing fixture is deliberately edited, use E2 in a new record and preserve its retention contract. E3 is optional for a consequential contextual disagreement. The exit claim can be “guidance and examples delivered, these issues inspected”; it need not claim improved future generations.

Stop or narrow the increment if it merely repeats existing guidance, cannot supply a meaningful counterexample or requires invented facts. Do not justify expansion by the number of sources already read.

## 3. WP-D: rendered annotations, not an omniscient audit

Static `audit` has a bounded source/CSS-import contract and cannot infer the complete browser cascade or user experience. Preserve LON-98/PR #2's separate scope. A future rendered annotation design should add explicit observed evidence without silently changing those claims.

An annotation binds source revision, capture hash, viewport, state, browser/environment and a target region. Coordinates use declared units and a fixed capture origin; a selector is supporting context, not proof the same element still exists. Findings contain evidence kind, actual observation, consequence, applicability and a recheck. An overlay is a presentation of an observation, not automatic defect detection.

Handle stale captures, missing elements, dynamic content, long pages, keyboard/focus state and inaccessible image loading explicitly. No screenshot-only check claims a successful submission or screen-reader experience. Keep annotation files separate from DNA and strict brief/config input. Validate path and image boundaries with Spec 13 if helpers are implemented.

Begin with one existing artifact and one named question. Cancel a general annotation platform if a short textual finding answers it. A future product API/CLI surface needs its own design review, compatibility analysis and documentation.

## 4. WP-E: effects chosen for a task

Motion may clarify sequence, status, spatial change or direct manipulation; it may also slow reading or distract. The RFC should define purpose, trigger, duration/easing where useful, interruption behavior, keyboard/pointer equivalents, reduced-motion fallback and a measurable performance budget appropriate to the actual product.

Static content and actions remain usable without the enhancement. Preserve truth: an animation cannot imply completed persistence, real-time presence or verified progress when none exists. Do not add a motion quota or a package of fashionable effects to make a design appear distinctive.

Entry evidence can be an available UX guideline plus a concrete task ambiguity. A small behavior regression is enough to establish implementation correctness; user-comprehension improvement requires separate evidence. Stop if the effect has no named benefit or the fallback loses information/function.

## 5. WP-F: task-matched diversity and retrieval

LON-99's composition-aware pilot is a reviewed increment, not proof that broad reference ingestion is finished. Future catalog additions should cover missing content relationships, task families and real composition decisions rather than adding more fonts or themes by count.

Record source family, rights, task fit, composition principle, legitimate limits and original wording. Deduplicate derived/reposted work. Preserve protected constraints, null reasons, source balancing and the existing offline/deterministic runtime. Existing family penalties and diversity counts are heuristics, not measured uniqueness guarantees.

Read specific upstream deltas when valuable. Do not install several overlapping skills or copy their instruction stacks. A coherent editorial repository can teach typography for a reading surface while being inappropriate for a dense operations app. Negative examples and conventional counterexamples belong alongside distinctive samples.

Optional retrieval should initially be a small index over curated cases. Embeddings, network search during normal CLI execution and background ingestion require a separate demonstrated need and architecture decision. Stop expansion when new records repeat existing decisions or rights cannot be established.

## 6. WP-G: language, delivery and hosts

LON-100 should specify the actual language/script coverage and font delivery being claimed. Vietnamese support needs rendered diacritics, real text and loading/fallback checks, not only a font's marketing language list. Keep original font license/provenance and avoid remote loads when the project requires offline delivery.

LON-101 native Windows filesystem/package behavior is distinct from successful Linux or WSL verification. Claim only environments actually checked. WSL mounted paths, Windows case rules, aliases and native package execution can differ. Preserve LON-95's exact tested host/version records; do not infer all-host certification.

A new host failure is diagnosed within that contract before broad refactoring. Unrelated UI research need not wait for universal host coverage. Public release scope must still disclose what is unsupported or unassessed.

## 7. WP-H/I: optional stronger evidence

Cost replication in LON-109 starts from full resource records, including invalid and failed segments, then selects comparable conditions. It cannot repair missing historical provider billing by estimation. A small supported claim is preferable to a fabricated global savings figure.

AI reviewer calibration can use known defects, legitimate conventional examples and disputed contextual cases. Measure missed known findings and overreach only within that challenge set; do not train an “AI-made” label or treat inter-model agreement as human truth. Keep calibration material separate from a later held-out comparison, or disclose overlap.

A fresh matched pilot enters Spec 12 E4 only for a question that matters after source/replay work. A targeted human study enters E5 only for a question about actual users that available research cannot adequately answer. Neither becomes a recurring requirement. If no such question remains, keep these packages dormant.

## 8. Distribution and release independence

LON-103 npm/distribution and LON-97 stable go/no-go retain their own source, package, host and publication requirements. A documentation or research PR does not change the release version. No merge, promotion or publish action is part of this roadmap.

For later skill changes, verify repository/package skill synchronization, appropriate validation, and offline CLI behavior. For code changes, run the relevant repository checks. Broad repeated testing is justified by actual changed behavior or unresolved concerns, not by the length of this roadmap.

## 9. Stop conditions and open decisions

Cancel or defer a package when it has no named decision, duplicates existing evidence, needs rights that are unavailable, exceeds its budget without reducing uncertainty, or produces a new abstraction without repeated need. Record why; cancellation is not failure to complete another package.

Open owner decisions are adoption of this design and selection of the next implementation package. Exact helper filenames, document layout and low-impact example wording are builder choices within approved constraints. Paid services, private-data exports, public schema changes, new mandatory study gates and release scope require explicit authorization appropriate to that action. No answer to those future choices is needed to deliver these specifications.
