# Proportional UI workflows

The current source makes TasteForge effort proportional to the task. The default uses one creator, a compact decision record and one focused correction/recheck. Additional research, prototypes or review are justified by an unresolved decision or demonstrated blocker. These effort levels are skill guidance, not CLI flags, new brief/DNA fields, global host settings or a resource guarantee.

## Choose the work

| Effort   | Typical use                                                  | Work boundary                                                                                                             |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Fast     | Bounded copy/component/focus/responsive correction           | Inspect target and existing context, edit, check affected states/widths. No mandatory plan, research or style generation. |
| Standard | New screen/flow with a reasonably clear structure            | Compact task/constraints/choice/check record, one coherent implementation, actual task/state/width review.                |
| Explore  | Consequential structure unresolved or alternatives requested | A small relevant evidence sample and two rough runnable task slices; choose and polish one.                               |

The user can request depth. A small change does not become a redesign because a heuristic fires, and a budget does not justify silently abandoning a known blocker. Human review and unsupported checks keep their actual status.

## Progressive context

Start with [the entrypoint](../skills/tasteforge/SKILL.md) and one relevant workflow. Read supporting references for a decision, normally one or two initially; expand when needed. Reuse product context, inspected sources, selected structure/tokens, last checks and open issues in existing guidance. Do not replay a conversation or create a long plan for a local edit.

Measured source size against commit948592b is1153→582 words for the entrypoint and12084→9979 words across Markdown resources. The new helper reference is included in the latter count. These are static word counts, not model-token usage, billed cost or proof of shorter runtime. Actual loaded resources/tool calls and host-exposed usage need separate measurement.

## Preserve quality with executable evidence

Relevant gates retain task/consequence clarity, edit/error recovery, minimum-supported-width behavior, factual product copy and applicable access checks. Default responsive helper widths320/390/1440 are configurable checks, not a universal support promise. Inspect intrinsic sizing and relevant decision/error/cart states; a full-page image does not establish viewport reachability.

The optional [browser helper](../skills/tasteforge/references/render-checks.md) runs with an existing Playwright installation and installs nothing. Its initial-page CLI reports geometry/navigation/JavaScript findings separately from unassessed dependencies. Existing task tests can import `captureCheckpoint` after real actions: natural scroll/focus is retained, viewport capture happens first, and optional full-page evidence has a separate scope. It neither proves a working interaction by itself nor certifies accessibility.

Read compact summaries and relevant frames first, opening full logs for diagnosis. Script assertions should establish actual behavior, not force exact failure wording or require all hidden state containers to have unique hooks.

## CLI and product truth

[Catalog use](../skills/tasteforge/references/catalog-use.md) distinguishes brief-free metadata retrieval from contextual `inspire`/generator setup. CLI use is optional; fixed constraints remain binding when a candidate is unavailable. Wait for actual process completion, retain exit/stdout/stderr and validate expected results. Empty redirected output is not a completion status.

Ground properties, policies, stock and guarantees in provided/inspected evidence. Expressive copy may change tone, not invent manufacturing details or financial certainty. A fixed illustrative conversion rate is not a guaranteed payout.

## Validation scope

The helper has meaningful fixture checks for real overflow/HTTP failure, natural scroll/focus and feedback, output reuse/traversal, compact output, missing dependencies/browser and optional axe findings/incomplete scope. Earlier diagnostics remain available in its recorded validation evidence. Independent old/new forward-tests are recorded separately from implementation validation; static reduction alone is not an efficacy claim.

The portable source skill includes these changes. Published `v0.2.0-beta.1` artifacts keep their tagged contents; package/engine/DNA versions and the six CLI commands are unchanged by this workflow update.

## Small forward-test

The [old-versus-lean probe](../evals/runs/2026-11-02-lean-workflow-probe/README.md) preserves two matched pairs. Fast corrections both passed42/42 scoped checks and changed onlyCSS. In one nativeAGY Standard pair, the lean initial generation reported20.1% fewer input tokens,12.4% shorter duration and34 versus49 native tool steps; output tokens increased3.5% and thinking-token usage increased35.5%. These are case-level observations, not a billed-cost or general efficiency guarantee.

Passing task/width checks was insufficient: rawStandard lean still had contrast, definition-list semantics and unsupported-rate wording. A separate worked finalization applies a focused correction and passes63/63 task/width checks with no reported axe violations in captured states; incomplete findings remain. This demonstrates closing known gates rather than approving a faster defective result. Its correction/evaluation costs are excluded from the initial paired metrics, so end-to-end accepted-UI savings are unmeasured. Historical/raw trials remain unchanged.
