# Create a new interface

1. Read the relevant project files. Identify the task, audience, language, content, technical constraints, and success condition. Ask only for missing decisions that materially change the interface; proceed with reversible assumptions when appropriate.
2. Start with realistic content and task order. Follow [research and structural planning](research-and-plan.md): inspect the user's references, research a few task-relevant examples when tools allow, compare genuinely different information/interaction structures, and record the selected structure in `UX_PLAN.md` or existing project guidance. Use [design principles](../references/design-principles.md) for unresolved decisions. Keep reference provenance and actual inspection scope.
3. For a substantial undecided layout, follow [structure and revision](structure-and-revise.md): try two runnable task slices with the same content and inspect wide/narrow decision states. Record the selection and tradeoff; skip redundant alternatives when existing constraints settle the structure. Then initialize the CLI without overwriting files, complete the brief, and suggest compatible visual directions if available. The CLI's visual candidates do not replace structural alternatives.
4. Select one coherent visual treatment. Generate Design DNA once a local direction fits the structure; use the recorded seed to reproduce it. If using `inspire`, inspect selected catalog entries and document the manual adaptation instead: external reference IDs are not token-generating direction IDs. External `DESIGN.md` documents can inform an attributed adaptation. Record intentional deviations, such as an existing brand accent or table-specific density rule.
5. Implement the main task with semantic controls, tokenized styles, and an accessible mobile reading order. Include empty, loading, validation, error, success, disabled, and focus states relevant to the task. Preserve content at zoom and with long translations. When the art direction calls for text, image or layout effects, use [effects and composition](../references/effects-and-composition.md) to choose a purpose and static fallback, then verify actual motion/input behaviour rather than copying a demo wholesale.
6. Run build and project checks, then the supported source audit. Complete the [render and revision pass](structure-and-revise.md#render-the-chosen-task-then-edit), recording the observed issue, actual artifact, change and rechecked result. Check task reachability, information relationships, consequence visibility, and narrow-screen priority separately from font/color polish. Report executed behavior, agent inspection and human/user testing separately.

Without the CLI, document the same design decisions in project guidance and keep the system small. Do not copy a landing-page recipe when the task calls for a form, comparison, or working tool.
