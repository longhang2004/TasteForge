# Refine one target for a stated outcome

Use for an existing screen, component or flow when the user asks for a clearer, quieter, simpler or better-adapted interface. Resolve the actual target and authorised scope first. Reuse existing tokens, behaviour, factual copy and product constraints. Read [surface purpose](../references/surface-purpose.md) when the visitor's success or the appropriate expression is unclear.

These are agent editing intentions, not new `tasteforge` CLI subcommands. A small correction should not trigger a new style generator, two prototypes, a rewritten design system or a mandatory product-context document.

## Choose the smallest relevant move

| Requested outcome    | Inspect / edit                                                                                                                      | Preserve / check                                                                                                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Reduce clutter**   | Identify repeated explanation, evidence, containers and navigation; remove or merge what has no distinct job                        | Essential facts, comparison, consequences, discoverable controls and recovery. Repeating a quantity at review can prevent a mistake; repeated labels can orient separate regions      |
| **Clarify meaning**  | Replace vague action labels, ambiguous units, duplicated help and unclear failure copy with the actual action/problem/next step     | Product truth and action semantics. A local record must not become a claim that an order/payment was sent. Keep required help, validation association and useful empty-state guidance |
| **Adapt to context** | Reconsider reading order, overview/detail relationship, width and control placement for real content, narrow screens, touch or zoom | Values, filters, selected identity, meaningful comparisons, focus and recovery. A full-page capture does not prove the control was exposed in the viewport                            |
| **Adjust emphasis**  | Rebalance competing headings, chrome, accents, imagery or effects around the target's primary work                                  | Existing brand/fixed choices and status distinctions. Quieter does not require monochrome; more emphasis does not require adding motion or larger typography                          |

Use more than one move only when the demonstrated issue needs it. No fixed colour/font/card quota applies. Reduce an obstacle rather than hiding necessary complexity or moving every decision behind a disclosure.

## Tie each edit to evidence

1. Read existing context and inspect the target. State the relevant visitor success, scope and concrete issue. For visual critique, first record task/design observations, then compare source/detector results; disclose when only source or old captures were available.
2. Keep a compact finding record: **target/state/width → evidence → user consequence → proposed edit → intentional exception or uncertainty**. Separate a verified source condition, a heuristic pattern and a question requiring rendered/user evidence. Prioritise blocked actions, misleading consequences and access failures ahead of aesthetic preference.
3. Make the scoped edit. Preserve the state path and meaningful information. If fixing it requires a broader redesign, explain that relationship; follow the existing authorisation rather than silently widening scope.
4. Recheck the affected task and states. For a material composition change, use [render and revision](structure-and-revise.md#render-the-chosen-task-then-edit). For a copy/focus correction, inspect the changed states at the relevant widths. Record the actual result and remaining questions.

Keep justified exceptions local: “Retain Inter because it is the fixed brand font”; “retain two labelled summary regions because users compare records while editing”; “retain a coloured error rule because it accompanies explicit failure text.” A count or detector warning alone does not establish a defect. If no meaningful issue is found, keep the target and say what evidence was inspected.

When presenting an annotated comparison, label the source state, width, screenshot scope and change. Different layout candidates are alternatives, not chronological before/after versions. An overlay is an explanation authored from evidence unless an actual detector produced it; do not imply it was automatically detected or user validated.
